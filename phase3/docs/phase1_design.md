# Phase 1 design: public-data municipality exploration for 20 cities

## Goal and boundary

Phase 1 completes one reproducible path:

```text
public data download
  -> deterministic normalization
  -> Knowledge Graph / NetworkX MultiDiGraph
  -> pandas and NetworkX analysis
  -> natural-language query plan
  -> structured evidence
  -> natural-language answer
```

The fixed seed is the 20 municipalities in `configs/phase1_cities.yml`: nine in
Hiroshima, three in Yamaguchi, three in Okayama, two in Shimane, two in Ehime, and
one in Kagawa. A diagnostic may propose a change with quantitative evidence, but it
must not silently edit the seed.

Phase 1 uses only public structured data: SSDSE-A-2026, 2020 Population Census
commuting/school OD, P05-22 municipal-office points, C28-21 airports, and the 2025
Airport Management Status workbook. Exact editions, URLs, terms, and transformations
are defined in `data/provenance/sources.yml`.

## Evidence contract

### Hard facts

Only source or computed structured values may affect filters, rankings, and scores:

- SSDSE source values and documented normalized features
- commuting and school OD counts
- municipal-office and airport reference-point coordinates
- straight-line distance
- bidirectional flow, weighted degree, PageRank, and community membership
- overall and category-specific similarity
- source-year and missing-value metadata

Every query result carries the source dataset/edition, metric definition, selected
input scope, applicable output unit, and the exclusion or missing-data rules needed
to interpret it. SSDSE source units that are not encoded in its CSV remain governed
by the official explanation document rather than being guessed by the pipeline.

### Soft knowledge

An LLM may understand intent or add clearly labelled background prose. Soft knowledge
does not enter a score, cannot override computed order, and is never persisted as a
graph fact. If a user asks for an uncollected condition such as nature or hot springs,
the answer labels it `not_available` while answering supported conditions separately.

## Data model

The graph is a `MultiDiGraph` so relation types stay separate.

| Node | Required properties |
|---|---|
| `Prefecture` | ID, name |
| `Municipality` | ID, municipality code, name, prefecture, representative point, SSDSE attributes |
| `Airport` | airport ID, name, latitude, longitude, airport type, source edition |

| Relation | Direction | Core properties |
|---|---|---|
| `IS_IN` | Municipality -> Prefecture | relation label, annotation weight |
| `COMMUTES_TO` | Municipality -> Municipality | commuters, year, source ID |
| `STUDIES_IN` | Municipality -> Municipality | students, year, source ID |
| `ACCESS_TO` | Municipality -> Airport | distance_km, distance method, point definitions |

Administrative and mobility relations are never blended in analysis. PageRank,
weighted degrees, and community detection project only `COMMUTES_TO` and
`STUDIES_IN`; `IS_IN` and `ACCESS_TO` cannot contribute weight.

## Deterministic transformations

### Municipality attributes

SSDSE rows are selected by the 20 reviewed municipality codes. Source item code,
label, and reference year remain traceable. The SSDSE CSV itself has no unit row, so
source-unit definitions are not invented and must be checked against the official
explanation document. Numeric conversion never imputes a source fact. Feature
construction applies a documented transformation per field:

- population or size measures: log where distribution requires it
- service counts: population- or household-normalized where the denominator is valid
- already defined rates: retain the source rate rather than normalize twice
- comparison features: standardize across the Phase 1 set
- missing values: median-impute only in the temporary comparison matrix and expose
  the imputation count and median in feature metadata; source facts remain missing

The supported similarity views are `overall`, `population`, `medical`, `education`,
`economy`, and `welfare`. Category membership and transformation metadata are part of
the result. There is no permanent, universal `livability_score`.

### Municipality representative point

The representative point is selected from P05-22, not generated by an LLM or an
opaque geocoder. The primary rule is facility class `P05_002=1` (main municipal
office) with an unambiguous municipality match. For a designated city, the named city
hall is used rather than a ward office or an average of ward offices. Missing or
ambiguous matches fail preprocessing and require a reviewed explicit mapping.

This point is an auditable city-hall proxy. It is not a claim about the geographic or
population centre of the whole municipality.

### Commuting and school OD

The 2020 Census Table 3 workbooks are residence-based:

- `source`: usual-residence municipality
- `target`: workplace or school municipality
- `commuters`: `11_15歳以上就業者`
- `students`: `R1_（別掲）15歳未満通学者を含む通学者`
- `total`: `commuters + students`
- `year`: 2020

Cross-prefecture rows are retained. Designated-city totals and wards are not counted
together. Self rows are excluded from the intercity graph because they represent
within-city activity and may also contain unknown/overseas workplace or school
allocations. The exclusion is explicit; it does not assert that all self-row activity
is invalid.

The analysis graph is the induced subgraph on the fixed 20 cities. Therefore
"strongest", centrality, and communities mean **among these 20 cities**, not among all
Japanese municipalities. Flows from seed cities to cities outside the seed may be
used only in a separate diagnostic proposing seed review.

### Airports and access

C28-21 supplies airport identity, type, operating status, scheduled-service flag, and
the official airport reference point. The 2025 management workbook supplies annual
passenger values after a reviewed one-to-one name match. Reference-year differences
remain visible.

For each municipality, Phase 1 computes great-circle distance with the Haversine
formula from the P05 main-office point to a C28 airport reference point. The nearest
eligible airport receives an `ACCESS_TO` relation. This is an auditable straight-line
proxy, not road distance, rail distance, terminal access, or travel time. Passenger
scale may be reported as a separate airport attribute; it must not silently replace
distance in an "airport is near" claim.

## Analyses

### Bidirectional exchange

For two distinct municipalities `A` and `B`:

```text
flow(A, B) = OD(A -> B) + OD(B -> A)
OD = commuters + students
```

Evidence returns both directions and both components, not only the summed rank.

### Mobility hubs

The mobility projection reports weighted in-degree, weighted out-degree, weighted
degree, and weighted PageRank. The selected weight (`total`, `commuters`, or
`students`) and damping/settings are recorded with the result.

### Cross-prefecture functional areas

Community detection runs only on the mobility projection. The algorithm, seed,
resolution, input weight, and normalization are recorded. A community is described as
cross-prefecture only when its member municipalities span two or more prefectures.
Community output is exploratory evidence, not a legal or administrative boundary.

### City similarity

Similarity is computed from the documented normalized SSDSE feature matrix. Results
include category, similarity, contributing fields, transforms, missing fields, and
comparison population/scale context. An "overall" result never substitutes for a
specific request such as medical similarity.

### Similar city with airport access

A natural-language request can combine criteria, for example similarity to Hiroshima
and shorter distance to an eligible airport. The planner produces explicit criteria;
the executor computes each criterion independently and returns a transparent ranking
or Pareto-style comparison. It does not create or persist a generic livability score.

## Query and response architecture

```text
User query
  -> Query Planner: intent, entities, criteria, unsupported conditions
  -> Query Executor: named pandas / NetworkX analysis functions
  -> Structured Evidence: values, ranks, units, sources, limitations
  -> Response Generator: Japanese answer from evidence
```

The LLM plans and explains; it does not calculate flow, PageRank, community,
similarity, distance, statistics, or missing values. An offline deterministic planner
may be used for reproducible acceptance tests, while an LLM adapter can produce the
same validated plan schema. The Phase 1 Azure OpenAI adapter uses chat completions
with a JSON response boundary. Its planner output is passed through
`validate_provider_plan`, and its response output is stored outside `hard_facts`.
Unknown intent or unsupported conditions fail clearly rather than triggering an
improvised fact.

## Phase 1 exclusions

- No Wikipedia collection or Wikipedia-derived graph facts
- GraphRAG is outside the Phase 1 data and execution path
- No route counts
- No road or rail travel-time estimate
- No nature, hot-spring, rent, climate, tourism, or disaster-risk dataset
- No fixed `livability_score`
- No LLM-generated statistical or geographic fact

## Acceptance gate

Phase 1 is complete only when the current project environment can download or verify fixed source files,
rebuild processed data, run tests, and answer all of the following with quantitative
evidence and scope labels:

1. The city with the largest bidirectional flow with Hiroshima
2. Mobility hubs around Hiroshima
3. Cross-prefecture mobility communities
4. Cities similar to Hiroshima overall
5. Cities with better airport distance than Hiroshima
6. Cities similar to Hiroshima with better airport distance
7. Cities medically similar to Hiroshima
8. All seven questions through natural-language input
9. Values, units, definitions, editions, and limitations supporting every answer

Failure of any item keeps Phase 2 closed.
